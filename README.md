# MenuTree AutoQA Agent

Tooling for the **MenuTree** release gate: an element-by-element,
depth-ordered inventory of an Android app, exported as the expected workbook
with a UVTA test case per row.

Two tools, answering different questions:

```bash
# THE GATE — walk the hand-authored sheet, assert every row is present
python tools/verify_menutree.py --spec MenuTree.xlsx --package <pkg> --serial <serial>

# DISCOVERY — find UI the sheet does not have yet
python tools/build_menutree.py --package <pkg> --serial <serial> --time-budget 1500
```

Verification is what can gate a release: the same rows are walked every run,
the denominator is fixed by the sheet, and a row that cannot be reached is a
named Fail rather than silently missing coverage. Discovery is not
reproducible run to run and should not be used as a gate — see
[docs/STATE_OF_PLAY.md](docs/STATE_OF_PLAY.md) §3.

The older DroidBot/UTG pipeline (`main.py`) is still here and still works; it
produces a screen *graph* rather than an element tree, and everything from §1
onward describes it.

## 1. Design principle: the LLM is not in the structural path

Test *steps* are derived from graph paths, not generated by a model. The same
crawl data always produces a byte-identical `.uvta` file, so a gate failure is
always attributable to the app, never to model variance.

```
[ Device / APK ]
       |
       v
 +-----------+
 |  Crawler  |  DroidBot DFS/BFS exploration -> droidbot_out/
 +-----+-----+
       |  utg.js (state graph)  +  events/*.json (view metadata)
       v
 +-----------+
 |  Parser   |  joins both on (start_state, stop_state, event_str)
 +-----+-----+     -> MenuTree: states, transitions, selectors
       |
       +----------------------------+
       v                            v
 +-----------+              +---------------+
 | Emitter   |              |   Coverage    |
 | BFS paths |              | vs. manifest  |
 | -> .uvta  |              | vs. baseline  |
 +-----------+              +-------+-------+
       ^                            |
       |  (optional, non-structural) v
 +-----------+                   GATE: pass / fail
 |LLM naming |
 +-----------+
```

**Coverage model:** one testcase per *actionable transition* (edge coverage).
Each testcase is the shortest path from the launch state to that transition's
source, plus the transition itself. Screen (node) coverage falls out for free.

## 2. Why DroidBot and not AutoDroid

[MobileLLM/AutoDroid](https://github.com/MobileLLM/AutoDroid) is a **fork of
DroidBot** pinned at March 2024. What it adds is `TaskPolicy` — an LLM agent
that pursues a *single natural-language task* and stops when it believes the
task is done. Its own README lists "not good at determining task completion"
as a known limitation.

That is the opposite of exhaustive coverage. Concretely:

- AutoDroid's installed entrypoint (root `start.py`, what `pip install -e .`
  wires to the `droidbot` command) **removed the `-policy` argument** and
  hardcodes `policy_name=POLICY_TASK`.
- Its inner `droidbot/start.py` is still vanilla upstream, so invoking the
  module directly gives you plain, stale DroidBot with none of AutoDroid's
  additions.
- Its exploration policies (`dfs_greedy`, `bfs_greedy`) are unchanged from
  DroidBot. There is no coverage improvement to gain.

**Use upstream `honeynet/droidbot`.** Borrow AutoDroid's *idea* — an LLM to get
past screens DFS cannot crack — as a targeted fallback policy, not as the
traversal engine. See section 6.

## 3. Setup

Requirements: Python 3.10+, Java, Android SDK with `platform-tools` on PATH.

```bash
python -m venv .venv
.\.venv\Scripts\Activate.ps1        # Windows
# source .venv/bin/activate          # Linux / macOS

pip install --upgrade pip
pip install -r requirements.txt
pip install git+https://github.com/honeynet/droidbot.git

# REQUIRED: upstream DroidBot is stale and will not start on a current
# dependency set. Re-run this after any droidbot reinstall.
python tools/patch_droidbot.py

cp config.yaml.example config.yaml
cp .env.example .env
```

### Two install snags you will hit on Windows

**`could not open 'droidbot/resources/DroidBoxTests.apk': Invalid argument`**
— Windows Defender blocks read access to that file, and the wheel build dies.
Nothing in DroidBot references it. Clone the repo, delete
`droidbot/resources/DroidBoxTests.apk`, and `pip install` the local clone.

**`ModuleNotFoundError: No module named 'androguard.core.bytecodes'`** —
androguard 4.x moved `androguard.core.bytecodes.apk` to `androguard.core.apk`;
DroidBot still uses the 3.x path and crashes on startup. `tools/patch_droidbot.py`
fixes this in place (idempotent, keeps a `.orig` backup).

Edit `.env` to set `TARGET_PACKAGE` and `DEFAULT_SERIAL`. `DEFAULT_SERIAL` is
required whenever more than one device is attached — `adb devices` to find it.

## 4. Running

### The MenuTree tools (back-ends C and D)

```bash
# Check the sheet parses correctly first. No device needed.
python tools/verify_menutree.py --spec MenuTree.xlsx --package <pkg> --dry-run

# Then the real run. Writes a COPY of the workbook; the original is untouched.
python tools/verify_menutree.py --spec MenuTree.xlsx --package <pkg> --serial <serial>

# Discovery, to find UI the sheet does not have.
python tools/build_menutree.py --package <pkg> --serial <serial> \
    --time-budget 1500 --max-depth 12
```

Both write to a per-run folder `output/<package>_<YYYYMMDD_HHMMSS_mmm>/`, so
no run ever overwrites another. `verify_menutree.py` exits 2 if any row fails.

Both take a **run lock** on the device: a second run against the same serial
is refused, naming the PID that holds it. `--force-lock` overrides. Both
release the device on exit — dropping the stay-awake hold, force-stopping the
app and going Home — from a `finally`, so an interrupted run still hands the
handset back.

> **Safety on a personal device.** The action guard is on by default and
> refuses destructive, outbound, account and commerce controls; keypad keys
> are recorded but never pressed (`*2767*3855#` is a factory reset). Do not
> pass `--no-guard` on a device holding real data.

### The DroidBot pipeline (back-end A)

```bash
python main.py                          # crawl -> parse -> emit -> gate
python main.py --skip-crawl             # re-derive from existing droidbot_out/
python main.py --crawl-only             # exploration only
python main.py --update-baseline        # record this run as the gate baseline
python main.py --config other.yaml --run-id nightly_42
```

**Exit codes**, for CI:

| Code | Meaning |
|------|---------|
| `0`  | Gate passed |
| `1`  | Pipeline error (crawl, parse, or emission failed) |
| `2`  | Gate failed — coverage below threshold, or regression vs. baseline |

Outputs: `out/*.uvta`, `reports/<run-id>.json`, `logs/<run-id>.log`.

### Establishing the gate

```bash
python main.py --update-baseline        # on a known-good build
python main.py                          # every subsequent build
```

The gate fails when testable coverage drops below
`coverage.min_activity_coverage`, or when any activity, transition, or
testcase reachable in the baseline is no longer reachable. Regressions name
the exact screen that was lost.

## 5. Reading the coverage report

Two different numbers, deliberately:

- **Crawl breadth** — activities the crawler physically reached. Measures how
  well exploration went.
- **Testable coverage** — activities reachable from launch by UI steps alone.
  **This is what the gate uses.** An activity the crawler stumbled into but
  that no emitted testcase can reach is not covered, and counting it would
  overstate the gate.

The gap between them is reported as *discovered but not testable* and is
always worth investigating: it usually means a screen is only reachable via a
deep link, a restart, or a state the crawl cannot reproduce.

`activities_missing` names screens declared in the manifest that were never
reached at all — the actual list of untested features. This requires the APK
manifest; it is populated automatically when the APK is pulled from the device.

## 6. Known gaps

These are real limits of the current pipeline, not aspirations:

1. **Generated tests are not replayed.** A `.uvta` file that has never been
   executed is a hypothesis. Add a replay pass (DroidBot has `POLICY_REPLAY`)
   and ship only verified-green tests.
2. **UVTA grammar is partly inferred.** Only `launch`, `click`, and
   `verify ... exists timeout` are confirmed from a worked example. Everything
   else in `src/generator/uvta_syntax.py` is marked `UNVERIFIED` — correct that
   one file and the whole generator follows.
3. **Jetpack Compose needs descendant label resolution.** Compose emits a
   bare clickable `android.view.View` whose content-description sits on a
   child node. On a real Compose app crawled during development, only **3 of
   16 clickable views** carried any identifier of their own; the parser now
   walks the subtree to recover the label (`parser.resolve_descendant_labels`).
   Controls that still resolve only to a `className` are reported as
   `ambiguous_transitions` — a coverage gap — rather than emitted as tests
   that would click an arbitrary match.
4. **Activity coverage is near-meaningless for single-Activity apps.** A
   Compose or Navigation-Component app may declare one Activity and hold
   dozens of screens. Gate those on `states_discovered` and
   `actionable_transitions` regression instead of activity percentage.
5. **Launch-transition frames.** DroidBot can capture a state after
   ActivityManager reports the app in the foreground but before it renders, so
   the state claims the app's activity while containing only launcher views.
   These are detected and pruned; left in, they become the graph root and
   prefix every testcase with a bogus launcher click.
6. **Semantic input is not handled.** DroidBot types the literal `"HelloWorld"`
   into every text field, which fails validation and silently costs whole
   subtrees. This is where an LLM fallback policy genuinely pays off: subclass
   `UtgGreedySearchPolicy`, keep DFS as the driver, and consult a model only
   when a state has been revisited N times with no new states discovered.
7. **Split APKs.** Preinstalled system apps are often split; androguard cannot
   read a split set as one file. The base APK is pulled and used, so activities
   declared only in splits will under-count. Set `crawler.apk_path` to a
   standalone APK when one exists.
8. **Screens DFS structurally cannot reach** — hardware states (no SD card, low
   battery), OS-level permission dialogs, and canvas-rendered surfaces with no
   view hierarchy. Enumerate these and either script them or declare them
   out of scope, so they do not silently deflate the number.
9. **Event file collisions.** DroidBot names event files with second-resolution
   timestamps, so two events in the same second overwrite each other. The
   parser warns when an edge has no matching event record; a persistent warning
   means raising `crawler.interval`.

## 7. Development

Device-free test entry points. Run them before any device work — they take
seconds and catch most regressions:

```bash
python tests/test_hierarchy.py     # XML parsing, state keys, Compose selectors
python tests/test_run_lock.py      # per-device mutual exclusion, stale locks
python tests/make_spec_fixture.py  # workbook shaped like the real deliverable
python tools/verify_menutree.py --spec tests/spec_fixture.xlsx \
    --package com.example --dry-run   # exercises the spec reader end to end

python tests/make_fixture.py       # synthetic droidbot_out/ in DroidBot's format
# then point config parser.output_dir at ./tests/fixture_out and:
python main.py --skip-crawl
```

### The experimental replay explorer

```bash
python tools/explore_u2.py --package <pkg> --serial <serial> --time-budget 900 --compare ./droidbot_out/<run>
```

`pm clear` before each replay is **on by default** — without it, any one-time
UI the app records as dismissed makes the recorded root unreachable and the
crawl silently collapses (measured: 71 of 74 replays discarded). Disable with
`--no-clear-between-paths` only if you understand that risk.

> **Safety:** an exhaustive crawler presses every button it finds. On the Phone
> app it dialled numbers. On a physical device that means *real calls*. Read
> [ARCHITECTURE §11](docs/ARCHITECTURE.md) before crawling on real hardware.

**Comparing crawlers:** never compare raw state counts between back-ends —
they use different state abstractions. Re-hash one crawler's saved hierarchies
with the other's `state_key` first. See ARCHITECTURE §6.1.

## 8. Troubleshooting

**`droidbot is not installed`** — `pip install git+https://github.com/honeynet/droidbot.git`

**`Expected exactly one online device...`** — set `DEFAULT_SERIAL` in `.env`.

**`Device 'X' is in state 'unauthorized'`** — toggle USB Debugging off/on and
accept the RSA fingerprint prompt.

**`Package 'X' is not installed`** — verify with
`adb shell pm path <package>`.

**`Device X is already being driven by PID N`** — a run is still live. Two
runs interleaving their taps on one handset corrupt both, invisibly. Stop the
named process (`taskkill /PID N /F` on Windows, `kill N` elsewhere) or pass
`--force-lock` if you are certain it is dead.

**The device keeps acting after a run finished** — check, in this order:

```bash
tasklist | findstr python                  # an earlier run still going?
adb shell dumpsys power | findstr mWakefulness
adb shell dumpsys deviceidle | findstr mScreenOn
adb shell settings get secure enabled_accessibility_services
adb shell ps -A | findstr -i "uiautomator atx droidbot monkey"
```

Two causes, both now fixed but worth knowing:

1. **An orphaned run.** With `--time-budget 7200` a run started two hours ago
   is still clicking long after you believe it finished. The run lock now
   prevents the overlap and names the PID.
2. **The app left open on a lit screen.** A run used to drop only the
   stay-awake hold, leaving the app in the foreground mid-menu. An OEM camera
   left open keeps auto-focusing, running scene detection and animating its
   viewfinder — indistinguishable from the tool still clicking. Release now
   also force-stops the app and presses Home.

To clean up by hand after an older build:
`adb shell svc power stayon false && adb shell am force-stop <package>`.

**`installed only as split APKs`** — supply a standalone APK via
`crawler.apk_path`.

**`utg.js not found`** — the crawl never brought the app to the foreground.
Check the `[droidbot]` lines in `logs/<run-id>.log`.

**Low coverage** — raise `crawler.count`, and leave `crawler.timeout: -1`. A
600-second budget is roughly 600 events, nowhere near exhaustive for a large
app. Check `transitions_skipped` in the report for what was dropped and why.
